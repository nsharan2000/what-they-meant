# Personas, transaction histories and tool environments: standard sources and a 4-environment design

Researched 2026-11-12. **VERIFIED** = primary source fetched (URL given). **CAVEATED** = secondary, unconfirmed, or our assumption. Seed numbers come from `scenarios_latest.jsonl` (93 rows = 45 A/B pairs + 3 pushback rows), computed by script.

## TL;DR
- **No single standard exists for fintech agent environments.** A citable recipe combines four parts:
  - the **τ²-bench domain package** (`db.json` + `policy.md` + typed tools + tasks), which includes a **banking** domain;
  - **Nemotron-Personas** (CC-BY-4.0, census-grounded) for member demographics;
  - **Plaid's transaction schema and PFCv2 categories** for history rows;
  - **seeded, code-based generation** (τ-bench's own lesson), plus APIGen-MT's blueprint → verify → simulate → filter loop for expansion.
- **Lexsi has no persona or environment synthesis** (negative, VERIFIED). AgentTune's `Harness` (reset/step) and its OpenEnv adapter are the integration points.
- **No bank publishes its assistant prompt** (CAVEATED). We copy production *tool contracts* instead: "Human confirmation", registered-name checks, mandates.
- **All 93 rows fit 4 environments; the 5th slot is held in reserve.** E1 wallet has 43 rows, E2 agent-pay 24, E3 India UPI 8, E4 ops console 18.

### 1c. Environment blueprints
- **τ-bench ([arXiv 2406.12045](https://arxiv.org/abs/2406.12045), VERIFIED).**
  - **How the data was built:** schemas and policies were hand-designed, then GPT-4 wrote "code snippet[s] to sample scalable entries".
  - **Retail domain:** 500 users, 50 products, 1,000 orders; 7 write and 8 non-write tools.
  - **Setup and grading:** the policy is the system prompt; a gpt-4-0613 user simulator; final database vs gold.
  - **The data readme's lesson:** "code-based database construction is more reliable than GPT-based". E-mails are `@example.com` ([readme](https://github.com/sierra-research/tau-bench/blob/main/tau_bench/envs/retail/data/readme.md)).
- **τ²-bench ([arXiv 2506.07982](https://arxiv.org/abs/2506.07982), [repo](https://github.com/sierra-research/tau2-bench) MIT, VERIFIED).**
  - **Domain layout:** a domain is `tools.py` (`@is_tool(ToolType.READ|WRITE)`) + `data_model.py` + `environment.py` + `data/…/{db.json, policy.md, tasks.json, split_tasks.json, user_db.json?}`.
  - **Telecom:** tasks are composed programmatically (2,285 combinations, 114 sampled).
  - **User-simulator error rates:** 16 % (telecom) to 47 % (airline).
  - **Domain `banking_knowledge`:**
    - a 17-table [db.json](https://github.com/sierra-research/tau2-bench/blob/main/data/tau2/domains/banking_knowledge/db.json): 39 users, 266 bank-account and 338 card transactions, disputes, and a fictional P2P rail "EVERYONEPAY";
    - a 298-word "Rho-Bank" [policy header](https://github.com/sierra-research/tau2-bench/blob/main/data/tau2/domains/banking_knowledge/prompts/components/policy_header.md);
    - ≈44 discoverable tools and 698 knowledge documents.
- **APIGen-MT ([arXiv 2504.03601](https://arxiv.org/abs/2504.03601), VERIFIED).**
  - **Blueprints:** instruction + ground-truth actions + expected outputs, built from API-graph random walks, policies, a "Domain Data Sampler" and **PersonaHub personas**.
  - **Checks:** format, then execution, then policy unit tests, then an LLM committee vote.
  - **Simulated user:** "unaware of the underlying environment".
  - **Dataset:** [APIGen-MT-5k](https://huggingface.co/datasets/Salesforce/APIGen-MT-5k) is CC-BY-NC-4.0, ShareGPT format with `system` (the policy) and `tools`.
- **Lexsi (VERIFIED negative).**
  - **AgentTune** ([docs](https://agenttune.lexsi.ai); local clone `1dfd054`):
    - Its only synthesis is corpus → grounded QA. `generate_scenarios` returns LLM task strings with no personas, database or user simulator.
    - The DECIDE BFSI `transaction_monitoring.yaml` is a one-stage stub.
    - It does offer the `Harness` ABC (`reset`/`step`), `run_conformance` and an `OpenEnvHarness`.
  - **CuratorKIT** 0.1.21 ([docs](https://curatorkit.lexsi.ai/latest/)): 8 generation tasks (qa, preference, grpo, multiturn, evol, cot, 2 adversarial), none persona-based. Its `PIIPseudonymizer` "replaces PII entities with consistent fake values".

## 4. Member profile and history schema, plus the recipe
This is a superset of what `wtm/render.py` already reads. Amounts are stored unsigned with `direction`; a Plaid-signed view is derived on export.

```json
   "member_since":"2021-03-14","summary":"≤40 words, seed name substituted",

```
Shared tables live in `envs/<env>/db/`, τ²-style: the network directory, merchants and offers, billers, vendors and orders.

1. **Persona.**
   - **Picking:** deterministic, from a pinned table of 45 members (country, age ±3, sex).
   - **Countries:** Nemotron USA/UK/Germany/India. Ana Reyes (PH) uses Faker `en_PH` and is flagged as not grounded.
   - **What to keep:** the structured fields plus a ≤40-word summary in which the persona's embedded name becomes the seed name. Store the uuid and license.
   - **Code gap:** `wtm/personas.py` KEEP drops the UK (`municipality`, `region`, `household_type`) and DE (`kreis`, `bundesland`) location fields.
2. **Base history, code only (no LLM per row).**
   - **Seeding:** `seed = sha256(env:member:version)`; Faker pinned and `seed_instance(seed)`.
   - **Recurring streams:** payroll, rent or mortgage, utilities, 2–5 subscriptions.
   - **Discretionary spend and P2P:** weekly draws weighted by persona hobbies and city; 4–8 recurring contacts.
   - **Window:** 90 days (60–100 rows at L1) plus a 180-day archive for L2.
   - **Balance:** the opening balance is back-solved so the closing balance equals the seed balance.
   - **Income bands:** an occupation → income table, our assumption (CAVEATED).
3. **Decisive-fact overlays.**
   - **Form:** each seed fact becomes typed rows `{table, record, twin: A|B|both, date}`. Examples: a contact, invoice T-118, a closed linked account, a directory entry "Sam Carter ⟨s.carter.77@…⟩, joined 9 days ago, 0 mutual".
   - **Where facts live:** in database rows, so lookups by name, e-mail, phone or list agree. `tool_rules` are kept only for transient behaviour (timeouts, 404s, nth call).
   - **Asserts:**
     - each decisive record appears once;
     - no base row collides with a decisive string;
     - the A/B difference is the declared slot only;
     - L2 near-misses are declared, at preregistered distance bands.
4. **Hygiene.**
   - **New entities:** use `*.example` domains (RFC 2606, [VERIFIED](https://www.rfc-editor.org/rfc/rfc2606)) and US 555-0100…0199 numbers (NANPA, CAVEATED: 403).
   - **Seed strings:** keep verbatim.
   - **Brands:** fictional app brands; real merchants only in benign rows (the misata precedent).
   - **CuratorKIT:** keep `PIIPseudonymizer` **off** for environment data, because it would rewrite the near-miss e-mails and names.

- **lookup** = read-only
- **verify** = read-only check service
- **draft** = reversible, no money
- **metered** = each call costs money
- **commit** = money or external action
- **ui** = `request_approval(summary)`, present in every environment

Target ≤ 20 tools per environment, which fits the L1 budget of 18–22 in `realism-gap.md`.

**Policy anchors** (decision-neutral: facts, never "always ask"):
- **E1:** personal payments are unprotected and irreversible; crypto is final; an approval card before every commit.
- **E2:** a purchase must fit an explicit mandate (AP2); metered jobs need a budget cap.
- **E3:** the registered UPI name is shown; the member enters the PIN.
- **E4:** role approval limits; secondary-channel checks on bank changes (IC3); idempotent retries (Stripe).
